# Build script `build.rs` в Rust: разбор

Твой проект `o_093` — рабочий пример полного цикла «C → статическая библиотека → Rust FFI». Разберём, что здесь важно, и уточним конспект.

## Почему в твоём проекте всё сработало

Связка трёх файлов:

| Файл | Роль |
|------|------|
| `native/distance.c` | C-код: структура `Point` + функция `distance` |
| `build.rs` | компилирует `distance.c` в статическую библиотеку через `cc` |
| `main.rs` | объявляет `extern "C"` и вызывает `distance` |

Ключевой момент — **`cc::Build::compile("distance")`** делает две вещи:

1. Компилирует `distance.c` в объектный файл.
2. **Автоматически печатает** `cargo:rustc-link-lib=static=distance` и `cargo:rustc-link-search=native=...` — то есть говорит Cargo слинковать получившуюся библиотеку с крейтом.

Именно поэтому тебе **не нужно** вручную писать `#[link(name = "distance")]` или `cargo:rustc-link-lib` — `cc` делает это за тебя. Это главная причина, почему `cc` — стандартный инструмент для C-зависимостей.

## `#[repr(C)]` — обязательное условие

```rust
#[repr(C)]
struct Point {
    x: f64,
    y: f64,
}
```

Без `#[repr(C)]` Rust **не гарантирует** порядок и выравнивание полей — компилятор может переставить их для оптимизации. C ожидает строго `x` затем `y`, и без `#[repr(C)]` данные были бы интерпретированы неверно. Это классическая ошибка FFI.

## `unsafe extern "C"` — что здесь важно

```rust
unsafe extern "C" {
    fn distance(a: Point, b: Point) -> f64;
}
```

- `extern "C"` — C ABI: соглашение о вызовах, порядок аргументов, способ передачи структур.
- `unsafe` — потому что Rust **не может проверить** корректность C-кода: сигнатуру, время жизни, побочные эффекты.
- Вызов `distance(pt1, pt2)` — тоже в `unsafe` блоке.

Важно: `extern "C"` **не проверяет**, что C-функция реально существует. Если символ не найден — ошибка линковки (`LNK2019`), как в твоём предыдущем случае.

## Уточнения к конспекту

### `cargo:rerun-if-changed` — не только для `.proto`

Ты упомянул `schema.proto`. На самом деле директива работает для **любого** файла:

```rust
println!("cargo:rerun-if-changed=native/distance.c");
```

Без неё Cargo по умолчанию перезапускает `build.rs` при изменении **любого** файла в пакете — это может быть дорого. Явное указание сужает отслеживание до нужных файлов.

**Важно:** `cc::Build` **не** добавляет `rerun-if-changed` автоматически для `.c` файлов. Если хочешь, чтобы изменение `distance.c` пересобирало проект, добавь директиву вручную:

```rust
fn main() {
    println!("cargo:rerun-if-changed=native/distance.c");
    cc::Build::new()
        .file("native/distance.c")
        .compile("distance");
}
```

### `cargo:rustc-env` — время компиляции, не выполнения

```rust
println!("cargo:rustc-env=BUILD_VERSION=1.0.0");
```

Переменная доступна через `env!` / `option_env!` **на этапе компиляции**:

```rust
const VERSION: &str = env!("BUILD_VERSION");  // "1.0.0"
```

В рантайме через `std::env::var("BUILD_VERSION")` её **не будет** — это не то же самое, что переменная окружения процесса.

### `OUT_DIR` — куда класть сгенерированный код

Ты упомянул `OUT_DIR`, но не показал, как его получить. Стандартный паттерн:

```rust
use std::env;
use std::path::PathBuf;

fn main() {
    let out_dir = PathBuf::from(env::var("OUT_DIR").unwrap());
    let dest = out_dir.join("generated.rs");
    std::fs::write(&dest, "pub const X: i32 = 42;").unwrap();
}
```

Затем в коде:

```rust
include!(concat!(env!("OUT_DIR"), "/generated.rs"));
```

`OUT_DIR` — это `target/debug/build/<crate>-<hash>/out/`. Cargo создаёт его автоматически.

### Полный список директив `cargo:`

| Директива | Назначение |
|-----------|------------|
| `cargo:rerun-if-changed=PATH` | перезапустить build.rs при изменении PATH |
| `cargo:rerun-if-env-changed=VAR` | перезапустить при изменении env-переменной |
| `cargo:rustc-link-lib=[KIND=]NAME` | слинковать библиотеку |
| `cargo:rustc-link-search=[KIND=]PATH` | добавить путь поиска библиотек |
| `cargo:rustc-cfg=KEY[="VALUE"]` | включить `cfg` для компиляции |
| `cargo:rustc-env=VAR=VALUE` | установить env-переменную на время компиляции |
| `cargo:rustc-flags=FLAGS` | передать флаги rustc (ограниченно) |
| `cargo:warning=MESSAGE` | вывести предупреждение |
| `cargo:metadata=...` | метаданные (реже используется) |

### `cargo:rustc-cfg` — пример

```rust
// build.rs
if cfg!(target_os = "windows") {
    println!("cargo:rustc-cfg=my_windows");
}
```

```rust
// main.rs
#[cfg(my_windows)]
fn platform_specific() { /* ... */ }
```

Это позволяет включать/выключать код на основе условий, вычисленных в `build.rs`.

### `cargo:warning`

```rust
println!("cargo:warning=Using fallback implementation");
```

Cargo покажет это как предупреждение при сборке. Полезно, когда `build.rs` выбрал неоптимальный путь.

## Когда `build.rs` — правильный инструмент

| Задача | Инструмент |
|--------|------------|
| Компиляция C/C++ кода | `cc` / `cmake` |
| Генерация кода из `.proto` | `prost-build` / `tonic-build` |
| Генерация кода из схем (flatbuffers, capnproto) | соответствующие `*-build` крейты |
| Условная компиляция по окружению | `cargo:rustc-cfg` |
| Версия из git | `git describe` + `cargo:rustc-env` |
| Генерация констант | запись в `OUT_DIR` + `include!` |

## Когда `build.rs` — плохой выбор

- **Простая логика без внешних зависимостей** — часто можно обойтись `cfg!` / `option_env!` без скрипта.
- **Генерация, которая может быть крейтом** — если есть готовый `*-build` крейт, не пиши свой велосипед.
- **Логика, зависящая от рантайма** — `build.rs` работает **до** компиляции, не путай с рантайм-конфигурацией.

## Практические правила

1. **Всегда добавляй `rerun-if-changed`** для файлов, от которых зависит сборка. Иначе Cargo перезапускает `build.rs` слишком часто (или слишком редко — если полагаешься на дефолт).
2. **`cc::Build::compile` сам печатает link-директивы** — не дублируй `cargo:rustc-link-lib`.
3. **`#[repr(C)]` обязателен** для структур, передаваемых в C.
4. **Ошибки FFI — через `LNK2019`**, а не компилятор Rust: сигнатура `extern` не проверяется.
5. **`OUT_DIR` — единственное правильное место** для сгенерированных файлов (не пиши в `src/`).
6. **`build.rs` замедляет сборку** — держи его минимальным, не тащи тяжёлые зависимости без нужды.

## Итог

- `build.rs` — скрипт, выполняемый **до** компиляции крейта; управляет Cargo через `println!("cargo:...")`.
- `cc` — стандартный способ компилировать C/C++ и автоматически линковать результат.
- `#[repr(C)]` + `unsafe extern "C"` — обязательная пара для FFI.
- `rerun-if-changed` — ключевая директива для корректной инкрементальной сборки.
- `OUT_DIR` + `include!` — стандартный паттерн для сгенерированного кода.
- В больших проектах `build.rs` часто собирает protobuf/flatbuffers/capnproto и кладёт результат в `OUT_DIR`.
